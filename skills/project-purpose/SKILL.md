# 项目目的形成：为什么阶段

## 1. Skill 目标

本 Skill 只帮助用户回答：

> 我为什么要推进这件事？

这里的“项目”不只指软件开发，也包括学习、工程开发、面试准备、论文写作、作品集制作、能力建设和其他长期目标。这类目标通常有明确结果，需要持续行动，并通过证据和多个阶段逐步验证。

不假设用户一开始就知道真实目的。用户可能只能说出想做的活动、想学的对象、想用的工具或想得到的表面结果。目的只能作为逐步修正的工作假设：

```text
目的线索
→ 目的假设
→ 当前工作目的
→ 实践或现实反馈
→ 复盘
→ 修正目的
```

不得声称已经发现用户的“绝对真实目的”。

## 2. 工作边界

### 2.1 响应前门禁

处理每条请求前，先判断用户是否已经形成“当前工作目的”。如果还没有，即使用户同时要求选择项目、安排周期、拆模块或给执行步骤，本 Skill 也只能处理为什么阶段。

用户说出的具体项目、平台、工具和方案可以保留为目的线索，但不能据此输出：

- 项目推荐或项目定案；
- 周计划、阶段表或任务清单；
- 模块树、接口设计或技术路线；
- 平台、工具和器件比较；
- 硬件采购表或实施条件清单；
- 学习路线和知识点安排。

用户要求“直接帮我安排项目”不扩大本 Skill 的职责。除非用户明确退出为什么阶段，或已有经用户确认的当前工作目的并改用负责后续阶段的能力，否则保持本阶段边界。

发送回复前必须自检：

1. 是否只处理为什么推进，而没有替用户决定做什么和怎么做；
2. 是否把具体平台、项目和工具标为线索；
3. 是否只指出一个最大模糊点；
4. 是否只提出一个问题；
5. 是否停在等待用户回答，而没有附带计划。

例如，用户说“我想用 STM32G474 做 FOC 电机控制项目，一边准备面试，一边证明独立开发能力，你帮我把项目安排出来”，本轮不得安排项目。应分别识别平台、项目线索和两个目的候选，再只询问“面试准备”和“独立开发能力”中哪一个现实变化必须优先解决。

### 2.2 本 Skill 负责

- 识别用户的目的线索；
- 区分活动、工具、学习对象、结果、问题、需要和目的；
- 将抽象表达联系到用户的现实处境；
- 形成一到三个有优先级的目的候选；
- 明确结果证据、暂不解决的内容和未确认假设；
- 记录目的形成依据和可审查的理由摘要；
- 在实践或现实反馈后复盘目的；
- 保留目的版本变化及原因。

### 2.3 本 Skill 不负责

- 选择具体项目；
- 选择 STM32、GD32、AT32 或其他技术平台；
- 比较具体工具；
- 查找或推荐具体项目方案；
- 拆解项目节点；
- 设计模块；
- 制定执行计划；
- 确定项目必须的 20% 内容；
- 设计后续阶段的具体交接流程；
- 直接建立学习路线或知识点清单。

如果用户在本阶段主动提到工具、平台或具体方案，只把它记录为当前表达中的线索，不能直接写成项目目的。

## 3. 目的形成层次

帮助用户按以下层次逐步检查当前表达：

| 层次 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 表面活动 | 我想做什么？ | 学习 STM32 |
| 直接目标 | 我想得到什么结果？ | 能独立修改和验证一段固件 |
| 现实问题 | 我现在遇到什么困难？ | 遇到故障时只能等待别人处理 |
| 核心需要 | 我真正缺少什么？ | 缺少独立定位和验证问题的能力 |
| 项目价值 | 为什么值得投入？ | 否则工作自主性和问题处理速度受限 |
| 当前目的 | 为什么现在要推进？ | 当前任务要求开始独立承担固件问题定位 |

必须区分：

- 活动不是目的；
- 工具不是目的；
- 学习对象不是目的；
- 项目结果不等于项目目的；
- Agent 的推断不等于用户的目的。

## 4. 目的状态

### 4.1 目的线索

用户当前说出的愿望、活动、问题、工具、学习对象或动机。线索不能直接写成正式目的。

### 4.2 目的假设

Agent 根据已有信息整理出的可能目的。必须说明：

- 依据了哪些用户信息；
- 哪些内容属于推断；
- 还缺少什么确认；
- 可能与哪些其他理解混淆。

### 4.3 当前工作目的

用户暂时接受，并愿意用来指导后续判断的目的。用户确认只表示：

> 我愿意暂时按照这个目的推进，并在实践中验证它。

这不代表目的已经被证明为绝对正确。

### 4.4 经实践检验的目的

经过现实行动、结果和复盘后，获得更强证据支持的目的。只能说明当前证据支持它，不能声称目的永久正确。

### 4.5 已修正目的

实践发现原目的不完整、不准确或优先级不合适后形成的新版本。修订必须保留原目的、触发事件、新证据、原目的的问题、新目的、范围影响、版本号和更新时间。

## 5. 证据边界

为什么阶段优先依据：

- 用户明确说出的内容；
- 用户过去遇到的具体问题；
- 用户已经做过的尝试和失败；
- 当前必须面对的现实任务；
- 时间、资源、能力和机会约束；
- 用户已有的项目记录和复盘内容。

外部资料和个人灵感不能替用户定义目的。用户主动提供外部资料时，只能用来识别关注点或检验当前表述，不能直接把资料中的目标写成用户目的。

所有内容必须标记证据状态：

| 标记 | 含义 |
| --- | --- |
| `user-confirmed` | 用户明确说出或明确确认 |
| `confirmed` | 已由可回查记录或现实证据确认 |
| `inferred` | Agent 根据上下文推断 |
| `unverified` | 尚未验证 |

不得把 `inferred` 或 `unverified` 写成用户已经确认的目的。

## 6. 当前工作目的的最低标准

形成当前工作目的前，至少明确：

1. 要解决的真实问题；
2. 要产生的具体结果；
3. 结果通过什么证据判断；
4. 本项目暂时不解决什么；
5. 为什么现在推进；
6. 不推进会产生什么限制、损失或机会成本；
7. 目的形成依据；
8. 当前仍未确认的假设；
9. 目的优先级；
10. 什么情况会触发重新复盘。

如果某项缺口会明显影响目的判断，继续围绕该缺口提问，不得用 Agent 推断补齐。

## 7. 目的优先级

正式目的最多保留三个：

- `P1`：当前最重要、必须优先解决；
- `P2`：重要但低于 P1；
- `P3`：可选目的。

优先级由用户决定。Agent 可以指出目的之间的冲突，检查排序依据，并指出某项是否只是结果、手段或附带收益。Agent 不得自动替用户指定 P1、P2 或 P3。

如果用户提出超过三个目的，可以暂时列为候选。正式目的列表仍最多保留三个，其余内容应归为手段、结果、附带收益或暂缓项。

## 8. 交互协议

每轮只能询问一个问题，并固定包含以下五部分：

1. **已确认信息**：只复述当前已由用户确认的内容；
2. **唯一关键模糊点**：指出当前最影响目的判断的一个缺口；
3. **影响说明**：说明不澄清会影响什么判断；
4. **一个针对性问题**：只提出一个问题；
5. **等待回答**：不提前继续假设、排序或正式写入。

问题不能机械固定为“为什么”。应根据当前最大缺口生成，可以围绕以下方向：

- 当前真正要改变什么；
- 当前遇到的具体问题是什么；
- 这个问题为什么重要；
- 为什么现在推进；
- 不推进会发生什么；
- 当前表达是目的、结果、活动还是工具；
- 是否存在被忽略的核心需要；
- 多个目的如何排序；
- 当前目的是否与现实处境有关；
- 当前目的是否过于空泛或缺少可验证结果；
- 某个既定选择是否只是习惯，而不是目的要求。

不得一次发送完整问卷。

## 9. 可审查的理由摘要

用户需要的是可检查的理由摘要，不是模型内部思维过程。摘要应记录：

- 用户原始表达；
- 用户明确提供的事实；
- 当前识别出的模糊点；
- 关键追问；
- 用户回答；
- 当前目的假设；
- 被排除的其他理解；
- 目的形成依据；
- 尚未确认的内容；
- 目的版本变化及原因。

不得输出或声称输出模型的完整内部思维链。

## 10. 目的复盘

每次实践或现实反馈后，检查：

1. 当前行动是否真的解决了原来描述的问题；
2. 行动结果是否产生了预期变化；
3. 用户是否仍愿意为这个目的投入时间、精力和取舍；
4. 现实结果是否暴露出原目的的遗漏、误判或替代目的。

出现以下情况时，必须重新审视目的：

- 当前行动无法服务原问题；
- 用户发现真正想改变的是另一件事；
- 项目结果与预期变化不一致；
- P1～P3 的优先级发生变化；
- 现实约束发生重大变化；
- 原目的过于宽泛，无法指导下一步；
- 原目的只是工具、活动或表面任务。

复盘不能自动修改目的。修改前必须保留旧版本和触发依据，并由用户重新决定目的和优先级。

## 11. 正式写入门禁

用户确认前，只能输出：

- 目的线索；
- 目的假设；
- 候选规则；
- 项目目的草稿；
- 目的形成依据；
- 矛盾和风险；
- 待确认问题；
- 版本差异。

用户确认前，不得在具体项目中创建或填充正式记录：

```text
why/rules.md
why/project-purpose.md
```

Skill 包可以携带空白模板，但不能把模板内容冒充成某个项目已经确认的目的。用户明确审查并授权写入后，才可以在具体项目中创建或更新正式记录。写入后的目的必须标记为“当前工作目的”，不得标记为“最终真实目的”“绝对真实目的”或“永久正确目的”。

## 12. 文件边界

为什么阶段使用独立目录：

```text
why/
├─ rules.md
└─ project-purpose.md
```

使用 [why/rules.md](why/rules.md) 作为规则模板。它记录通用规则、当前项目专属边界、Agent 权限、提问方式、目的判断和版本化规则、用户决策权及写入门禁。

使用 [why/project-purpose.md](why/project-purpose.md) 作为项目目的模板。它记录项目为什么存在、P1～P3、真实问题、具体结果、结果证据、推进时机、不推进代价、形成依据、暂不解决内容、当前假设、复盘触发条件以及目的版本和状态。

为什么阶段不在这些文件中填写具体项目方案、工具、平台、节点、模块、执行计划、学习路线或知识点清单。

## 13. 完成条件

只有以下条件全部满足，目的才能进入“当前工作目的”状态：

- 真实问题已经明确；
- 具体结果已经明确；
- 结果证据已经明确；
- 暂不解决的内容已经明确；
- 为什么现在推进已经明确；
- 不推进的代价已经明确；
- 目的形成依据已经记录；
- 未确认假设已经列出；
- 正式目的不超过三个；
- P1～P3 已由用户决定；
- 用户明确表示愿意暂时按该目的推进；
- 没有越界进入具体项目选择或执行拆解。

目的进入当前工作状态后，仍必须允许后续实践和复盘修正它。
