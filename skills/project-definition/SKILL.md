# 项目定义：是什么阶段

## 1. 目标

本 Skill 只帮助用户回答：

> 这个项目是什么？

最终需要说明：

- 项目为什么能够推进当前目的；
- 项目由哪些部分组成；
- 每个部分负责什么、不负责什么；
- 各部分之间是什么关系；
- 项目与外部环境的边界是什么；
- 项目具有什么具体特点；
- 当前版本必须包含什么；
- 当前版本暂时不包含什么。

本 Skill 不实现项目，也不判断项目是否已经完成。

项目后续是否成功，最终看它是否实现或推进了项目目的，而不是只看功能数量、代码量或任务完成率。

## 2. 阶段位置

项目指导分为三个阶段：

```text
project-purpose
→ 为什么阶段：明确为什么推进

project-definition
→ 是什么阶段：明确具体项目是什么

怎么做阶段
→ 在已确认框架内分析、设计、实现和验证
```

本 Skill 只负责“是什么阶段”。

为什么阶段统一交给 `project-purpose`。

## 3. 入口门禁

开始前，先确定用户具体项目的根目录。

必须读取：

```text
<项目根目录>/why/project-purpose.md
```

从中检查：

- 当前工作目的；
- 项目的实际用途；
- 要解决的现实问题；
- 希望产生的结果；
- 结果如何判断；
- 项目暂时不解决的内容；
- P1、P2、P3 及其用户确认的优先级；
- 目的状态和用户确认记录。

只有目的达到“当前工作目的”“经实践检验的目的”或“已修正目的”，并且上述字段足够支持项目选择时，才能进入本阶段。

以下内容不能作为入口：

- 目的线索；
- 未经用户确认的目的假设；
- Agent 推断；
- 模糊愿望；
- 技术名词；
- 工具偏好；
- 学习对象；
- 表面活动。

入口不满足时，输出：

> 当前项目目的还没有达到项目定义的入口条件，需要先回到为什么阶段确认项目目的。

随后交回 `project-purpose`。

不得自行补齐目的，不得替用户排序 P1、P2、P3。

如果项目目的发生变化，停止当前项目定义。先回到为什么阶段确认新目的。

## 4. 恢复已有工作

入口通过后，检查：

```text
<项目根目录>/what/rules.md
<项目根目录>/what/project-definition.md
```

文件存在时：

1. 读取 `what/rules.md`；
2. 读取当前 `what/project-definition.md`；
3. 检查版本和状态；
4. 读取“项目定义阶段进度”；
5. 找到上次正式保存的暂停位置；
6. 继续尚未完成的定义工作。

不要重新收集已经记录且仍然有效的信息。

第二次确认前的聊天草稿不写入项目文件。因此，不得声称这类草稿可以只靠项目文件跨会话恢复。

如果用户要求确认前也能跨会话恢复，先停止并询问允许使用的草稿保存位置。每轮仍只能问一个问题。

## 5. 职责边界

### 5.1 本 Skill 负责

- 根据项目目的形成项目选择标准；
- 形成或整理 2～3 个候选项目；
- 比较候选项目；
- 分析已经存在的参考素材；
- 分开记录用户个人灵感；
- 整理用户确认的项目选择；
- 定义项目整体框架；
- 定义组成部分和职责边界；
- 定义各部分之间的关系；
- 定义项目外部边界；
- 定义具体项目特点；
- 定义最小可行项目；
- 定义当前暂不包含内容和未来扩展；
- 维护项目定义版本和本阶段进度。

### 5.2 不负责为什么阶段

不得：

- 重新追问为什么要做项目；
- 重新定义项目目的；
- 自动决定 P1、P2、P3；
- 修改 `why/rules.md`；
- 修改 `why/project-purpose.md`；
- 记录目的推进结果；
- 记录用户能力提升程度。

发现目的变化时，停止并交回 `project-purpose`。

### 5.3 不负责怎么做阶段

不得：

- 拆项目节点；
- 拆任务或实施步骤；
- 设计具体模块实现；
- 设计代码接口；
- 制定开发计划或时间表；
- 设计具体测试任务；
- 管理实现进度；
- 判断实现阶段是否完成；
- 修改怎么做阶段的文件。

允许定义概念性的组成部分，但不能把它们继续拆成实施任务。

### 5.4 不负责搜索

不得：

- 搜索外部项目；
- 搜索论文、文章或视频；
- 选择搜索工具；
- 设计搜索流程；
- 管理搜索结果文件。

宿主可以另外使用搜索能力准备资料。本 Skill 只读取已经保存的结果。

素材不足时，写明：

> 参考素材不足，当前只能形成初步项目定义。

不得虚构素材、引用或搜索结果。

## 6. 证据规则

所有关键判断使用以下标签：

| 标签 | 含义 |
| --- | --- |
| `user-confirmed` | 用户明确提出或确认 |
| `confirmed` | 已由项目文件或参考素材确认 |
| `inferred` | 根据目的、素材和灵感推导 |
| `unverified` | 当前缺少足够证据 |

每项推荐、框架判断、边界和特点都要说明：

- 依据了什么；
- 来源在哪里；
- 哪些是用户确认；
- 哪些是资料确认；
- 哪些只是推导；
- 还缺少什么证据；
- 证据不足会影响什么判断。

`unverified` 不能单独作为最终推荐依据。

不得把参考项目的特点写成当前项目已经具备的特点。

## 7. 项目选择标准

项目选择必须首先服务 P1：

```text
P1：项目必须直接推进。
P2：项目可以兼顾。
P3：只能作为可选扩展。
```

比较标准至少包括：

- 是否直接服务 P1；
- 是否可能实现或推进当前目的；
- 是否有足够证据；
- 是否符合当前实际条件；
- 是否有清晰的最小可行范围；
- 是否容易通过实践检验；
- 是否可以继续迭代；
- 是否能形成清晰的整体框架；
- 是否能定义明确的组成和边界；
- 是否存在明显的不适用条件。

不能因为项目“看起来有意思”就推荐。

证据不足时，只能写成候选或推导，不得直接写成“最适合”。

## 8. 候选项目

用户没有候选时，根据以下信息形成 2～3 个候选：

- 当前项目目的；
- P1；
- 用户灵感；
- 用户已经提供的资料；
- 已经保存的参考素材；
- 用户明确提出的方向。

每个候选记录：

- 项目名称；
- 要解决的问题；
- 适用场景；
- 如何推进 P1；
- 项目整体形态；
- 主要组成部分；
- 项目特点；
- 所需前提；
- 当前已知限制；
- 仍缺少的证据；
- 可能适合的原因；
- 可能不适合的原因；
- 每项内容的证据状态。

候选只是待选方案。不得把候选写成用户已经拥有或已经完成的真实项目。

用户已经提供 2～3 个候选时，直接比较，不重复生成。

## 9. 参考素材

参考素材可以包括：

- 参考项目；
- 文献或文章；
- 视频；
- 用户已经保存的其他资料。

参考项目通常保留 3～5 个：

- 少于 3 个：标记参考项目不足；
- 多于 5 个：按代表性保留 3～5 个，并说明取舍依据；
- 文献、文章和视频不设固定数量；
- 无关素材不能为了凑数量加入。

每份素材记录：

- 素材名称；
- 素材类型；
- 来源；
- 文件路径或链接；
- 素材用途；
- 素材整体结构；
- 主要特点；
- 可借鉴内容；
- 不适用内容；
- 对当前项目定义的影响；
- 证据状态。

只记录索引和分析结论，不复制素材全文。

参考素材保留在原位置，不复制进 `what/`。

## 10. 用户个人灵感

用户灵感必须与参考素材分开记录。

每条灵感记录：

- 用户原始表达；
- 产生背景；
- 想解决的问题；
- 与项目目的的关系；
- 借鉴了哪些素材；
- 已经明确的部分；
- 仍然只是设想的部分；
- 是否采用；
- 不采用时的原因；
- 对项目结构的影响；
- 证据状态。

不得把 Agent 整理后的文字冒充成用户原话。

## 11. 第一次确认：候选项目方向

完成候选比较后，输出：

- 2～3 个候选项目；
- 各候选的证据；
- 比较结果；
- 推荐方向；
- 推荐依据；
- 仍缺少的证据。

等待用户确认候选方向。

用户确认前：

- 不进入完整项目结构定义；
- 不正式写入 `what/project-definition.md`；
- 不归档任何文件。

用户确认后，草稿状态为：

```text
candidate-confirmed
```

该状态只代表候选方向已确认，不代表完整项目定义已确认。

## 12. 完整项目定义

候选方向确认后，定义：

- 项目整体是什么；
- 项目解决什么问题；
- 项目服务哪个目的；
- 项目接受什么输入；
- 项目产生什么结果；
- 项目由哪些部分组成；
- 每个部分负责什么；
- 每个部分不负责什么；
- 各部分之间的关系；
- 项目与外部环境的边界；
- 项目内部边界；
- 当前必须包含什么；
- 当前暂不包含什么；
- 哪些内容属于未来扩展。

允许定义概念组成，例如：

```text
问题场景
实践对象
分析过程
结果记录
```

不得继续拆成：

```text
创建工程
实现模块
编写代码
执行测试
```

后一类内容属于怎么做阶段。

## 13. 项目特点

每个特点必须记录：

1. 特点是什么；
2. 它的具体含义；
3. 为什么适合当前目的；
4. 在项目中如何体现；
5. 当前依据是什么；
6. 是否由用户确认；
7. 是否仍需实践验证；
8. 证据状态。

不得只写“真实”“系统”“有趣”“可扩展”等空泛形容词。

## 14. 最小可行项目

本阶段的最小可行项目指：

> 用尽量少的投入验证项目目的，并让目的得到实现或推进的项目框架。

它不等于：

- 代码最少；
- 模块最少；
- 功能最少；
- 完成率最高。

每轮只定义：

- 当前必须保留的部分；
- 当前必须明确的边界；
- 可以进入怎么做阶段的最小框架；
- 需要实践验证的内容；
- 未来可能扩展的内容；
- 当前暂不包含的内容。

本 Skill 不记录功能完成率、任务完成量、代码量或实现进度。

## 15. 第二次确认：完整项目定义

完整草稿形成后，将状态标为：

```text
definition-draft
```

向用户展示完整项目定义，等待确认。

用户确认后：

1. 检查当前正式版本；
2. 必要时归档旧版本；
3. 写入新的 `what/project-definition.md`；
4. 状态更新为 `confirmed`；
5. 记录版本和用户确认内容；
6. 允许怎么做阶段读取。

没有明确确认时，不得正式写入，不得归档。

## 16. 固定文件结构

用户项目使用：

```text
<项目根目录>/
├─ why/
│  ├─ rules.md
│  └─ project-purpose.md
├─ what/
│  ├─ rules.md
│  ├─ project-definition.md
│  └─ archive/
└─ ...
```

一个项目根目录只对应一套 `why/`、一套 `what/` 和一份当前项目定义。

不同项目不得共用同一份 `project-definition.md`。

不要在 Skill 包中创建用户项目的 `what/` 文件。

## 17. `what/rules.md`

`what/rules.md` 记录：

- 阶段目标、入口和出口；
- 与为什么阶段、怎么做阶段及搜索工作的边界；
- 候选生成和比较规则；
- 推荐证据规则；
- 素材和灵感记录规则；
- 框架、边界和特点定义规则；
- 两次确认规则；
- 写入、版本和归档规则；
- 本阶段进度和恢复规则；
- 证据状态；
- 用户和 Agent 的职责。

只有用户明确要求修改“是什么阶段”的规则时，才更新该文件。

项目定义内容变化不能自动修改规则文件。

## 18. `what/project-definition.md`

固定章节为：

```text
1. 文档状态与当前版本
2. 项目目的来源
3. 项目选择标准
4. 候选项目
5. 候选项目比较
6. 被排除的项目及原因
7. 参考素材索引
8. 参考项目分析
9. 参考文献和文章分析
10. 参考视频分析
11. 用户个人灵感
12. 最终项目定义
13. 项目整体框架
14. 组成部分及职责边界
15. 部分之间的关系
16. 项目外部边界
17. 项目暂不包含内容
18. 项目核心特点
19. 当前假设与未决问题
20. 项目定义阶段进度
21. 项目定义版本记录
22. 用户确认记录
```

“项目定义阶段进度”只能记录：

- 当前定义环节；
- 已完成的定义内容；
- 尚未完成的定义内容；
- 当前待确认内容；
- 当前暂停位置；
- 下一步继续定义什么；
- 恢复需要读取哪些文件和信息。

不得记录项目实现进度、代码完成度、操作进度、用户能力变化、目的推进结果或怎么做阶段反馈。

## 19. 状态、版本和归档

支持以下状态：

| 状态 | 含义 |
| --- | --- |
| `draft` | 正在形成项目候选 |
| `candidate-confirmed` | 用户确认了候选方向 |
| `definition-draft` | 完整定义已形成但尚未确认 |
| `confirmed` | 当前正式定义 |
| `revision-required` | 用户要求重新定义，或整体框架和边界需要重新审查 |
| `archived` | 旧版本已归档 |

新项目默认从 `v0.1` 开始。后续版本号先提出，再由用户确认；不得自行发明版本含义。

归档目录固定为：

```text
what/archive/
```

文件名格式：

```text
rules-v<版本>-<YYYY-MM-DD>-<原因>.md
project-definition-v<版本>-<YYYY-MM-DD>-<原因>.md
```

归档规则：

- 只有规则更新时，才归档旧 `rules.md`；
- 只有正式项目定义更新时，才归档旧 `project-definition.md`；
- 用户确认新版本后才能归档；
- 先验证归档成功，再覆盖当前正式文件；
- 两类文件分别归档，互不绑定；
- 草稿不归档；
- 归档文件不再作为当前有效输入；
- 当前有效版本始终保留在固定路径；
- 归档失败时停止写入，不覆盖旧文件。

## 20. 单一问题规则

每轮只询问一个问题，并按以下顺序输出：

1. 已确认信息；
2. 当前唯一关键模糊点；
3. 该模糊点会影响什么；
4. 一个具体问题；
5. 等待用户回答。

不要发送完整问卷。

问题优先处理最影响项目选择、整体框架或边界的缺口。

## 21. 阶段出口

只有以下内容都已完成，项目定义才可以交给怎么做阶段：

- 项目目的入口仍然有效；
- 候选方向已经确认；
- 最终项目已经明确；
- 整体框架已经明确；
- 组成部分和职责边界已经明确；
- 各部分关系已经明确；
- 外部边界已经明确；
- 当前暂不包含内容已经明确；
- 项目特点已经有证据；
- 当前假设和未决问题已经记录；
- 完整项目定义已经由用户确认；
- 正式版本已经写入固定路径。

怎么做阶段自行读取：

```text
<项目根目录>/what/project-definition.md
```

不要依靠 Agent 临时上下文传递正式项目定义。
