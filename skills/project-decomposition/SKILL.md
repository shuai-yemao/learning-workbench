# 项目分解：怎么做阶段

## 目标和位置

本 Skill 只回答：

> 在已经确认的项目框架和边界内，项目大致需要按什么顺序推进？

固定阶段关系为：

```text
project-purpose：为什么推进
→ project-definition：项目是什么
→ project-decomposition：项目大致怎么推进
```

输出范围为：

```text
里程碑
→ 进度节点
→ 既定项目部分及细分
→ 操作大纲
→ 知识点
→ 技能
```

操作大纲只说明大致处理什么、为什么处理、期望什么子结果，以及前后、影响和回退关系。它不是操作手册。

## 正式入口

先确定具体项目根目录，再读取：

```text
<项目根目录>/what/project-definition.md
```

不得使用聊天上下文、Agent 记忆或临时推断代替该文件。入口至少确认：

- 文档状态为 `confirmed`；
- 项目整体框架完整；
- 顶层项目部分及其职责完整；
- 部分之间的关系明确；
- 项目外部边界和内部边界明确；
- 当前版本必须包含和暂不包含的内容明确；
- 用户确认记录存在。

章节存在但内容为空，不算通过。

入口不满足时立即暂停。只说明缺少什么、为什么它阻塞怎么做阶段，以及需要回到 `project-definition` 补充什么。不得继续分析里程碑、节点、项目部分、操作大纲或能力。

## 初始项目和老项目

检查：

```text
<项目根目录>/how/project-plan.md
```

文件不存在时按初始项目处理：读取项目定义，确定项目起点，提出起始里程碑草稿，并等待第一次确认。

文件存在时按老项目处理：

1. 读取旧计划的版本、分析状态、里程碑、节点、项目部分和暂停位置；
2. 不把旧计划中的历史位置当成当前真实进度；
3. 每轮只问一个问题，请用户提供当前已产生的关键结果和可检查证据；
4. 比较旧记录和当前输入，列出差异；
5. 用户确认当前进度差异后，再分析当前里程碑。

当前真实进度只记录选择里程碑所需的关键结果和证据。不得维护任务完成率、代码完成率、操作流水或用户掌握度。

## 三次确认

### 第一次：起始里程碑

里程碑只说明项目当前要推进到什么结果、处于什么进度位置，以及达到什么条件可以进入下一阶段。

里程碑草稿必须包含：名称、进度结果、当前位置、进入依据、完成条件、已知阻塞、关联项目部分、证据状态、依据来源和确认记录。

用户确认前不得拆进度节点、项目部分、操作大纲、知识点或技能，也不得写正式项目文档。

### 第二次：进度节点和项目部分

第一次确认后，固定按以下顺序分析：

```text
已确认里程碑
→ 进度节点
→ 对应的既定项目部分
→ 既定项目部分的细分
```

顶层项目部分必须来自 `what/project-definition.md`。可以选择、细分、排序并分析依赖和影响，但不能新增或删除顶层部分，不能改变原始职责、上层框架或项目边界，也不能把分析写回 what 阶段。

第二次确认同时检查节点、对应部分、细分、先后关系、影响、当前暂缓部分和是否越界。确认前不得提取操作大纲、知识点或技能。

### 第三次：操作大纲和能力

第二次确认后，为每个已确认的项目细分提取操作大纲。随后分别提取知识点和技能，并分别使用“必须、辅助、扩展、深入”四级分类。

第三次确认检查：

- 操作大纲及其顺序是否合理；
- 影响和回退是否明确；
- 知识点和技能是否分开；
- 四级分类是否合理；
- “必须”能力是否只保留当前真正需要的少量内容；
- 是否出现项目外内容；
- 每项判断是否有证据状态和依据来源。

第三次确认前只能输出草稿。确认后才能形成完整正式版本。

## 操作大纲和能力

需要起草、审查或写入操作大纲、能力清单及后续交接时，读取 [references/document-contracts.md](references/document-contracts.md)。

操作大纲不得包含：

- 软件点击步骤；
- 具体命令；
- 具体代码行；
- 表格填写步骤；
- 工具操作说明；
- 具体测试执行过程。

知识点回答“需要理解什么”。技能回答“需要形成什么可观察能力”。两者不得合并。

只有不具备就无法理解或推进当前大纲的内容，才能列为“必须”。“相关”“常见”或“完整课程里包含”不能作为必须依据。

## 证据规则

统一使用：

| 状态 | 含义 |
| --- | --- |
| `user-confirmed` | 用户明确提出或确认 |
| `confirmed` | 正式项目文档或可靠资料确认 |
| `inferred` | Agent 根据正式输入推断 |
| `unverified` | 尚未得到确认或证实 |

每条里程碑、进度节点、项目部分、操作大纲、知识点和技能都必须记录证据状态和依据来源。依据至少指向项目文档章节、既定项目部分、项目边界、某次用户确认或某条操作大纲。

不得把 `inferred` 或 `unverified` 写成用户已经确认。

## 一次只问一个问题

信息不足时，每轮固定包含：

1. 已确认信息；
2. 当前唯一关键缺口；
3. 该缺口会影响什么；
4. 一个具体问题；
5. 等待用户回答。

用户回答前，暂停所有依赖该信息的分析。

## 文件和状态

项目目录使用：

```text
<项目根目录>/how/
├─ rules.md
├─ project-plan.md
└─ archive/
```

需要创建或审查 `how/rules.md` 时，先读取 [references/how-rules-template.md](references/how-rules-template.md)。需要创建、恢复或审查 `how/project-plan.md` 时，先读取 [references/project-plan-template.md](references/project-plan-template.md)。

`project-plan.md` 只使用以下分析状态：

```text
未开始
里程碑分析中
待确认里程碑
进度和项目部分分析中
待确认项目部分
操作大纲和能力分析中
待确认操作方案
已确认
已暂停
```

这些状态只表示本 Skill 的分析进度，不表示项目实际执行进度。

## 写入和归档

第一次确认前不写正式文件。

第二次确认后：

- 初始项目只有在用户明确授权时，才可以写入包含已确认内容的阶段版本；
- 老项目不覆盖旧版，只保留待第三次确认的完整草稿。

第三次确认后：

1. 确定新版本号；
2. 老项目先把旧 `project-plan.md` 归档到 `how/archive/`；
3. 重新读取归档文件，确认内容完整；
4. 再写入新的 `project-plan.md`；
5. 重新读取当前文件，检查版本、状态和确认记录。

首次正式版本直接写入，不归档不存在的旧版本。草稿修改不触发归档。归档失败时停止，不覆盖当前文件。

`how/rules.md` 只有在用户明确确认规则创建或规则变化后才能写入。规则文件和项目计划分别归档，互不绑定。

## 后续交接和边界

正式计划必须包含知识学习交接和技能训练交接。本 Skill 只写交接内容，不自动调用 `knowledge-point-learning`，不开始教学、训练或项目执行。后续 Skill 必须重新读取正式 `how/project-plan.md`。

本 Skill 还不得：

- 修改 `why/` 或 `what/` 文件；
- 重新定义项目目的、P1～P3、上层框架或项目边界；
- 选择新的具体项目；
- 记录用户实际完成了多少操作；
- 判断用户已经掌握知识或技能。

项目目的变化时返回 `project-purpose`。项目框架、顶层部分、职责或边界需要变化时返回 `project-definition`。

创建、修改或审查本 Skill 时，读取 [references/acceptance-scenarios.md](references/acceptance-scenarios.md)。格式校验不能替代这些行为场景。
